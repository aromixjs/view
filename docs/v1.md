Supersedes v0.2 entirely. The binding syntax, wire protocol, and
cross-component mechanism below have been run as working code — real
server, real HTTP requests, real class instances — not just designed on
paper. Where it matters, the working example is shown alongside the spec.

---

## 0. Core idea

A component is an ordinary class. No base class, no `props!` declaration,
no metadata object the author writes by hand — just a constructor and
methods. The compiler reads that class once and generates everything the
runtime needs: which fields are props, which are state, and what each
method touches. At request time, only the one instance whose method was
clicked ever gets constructed — never a tree, never a snapshot — and if
that method calls a prop that was wired to a parent's method, that call
is a real function call, because the runtime builds it as a real
closure. Nothing about a callback prop is a special case anywhere in
this system; it's just a function, like any other.

---

## 1. Author syntax

This is plain TypeScript. The only non-standard piece is the `av!{}`
macro around the returned markup.

```tsx
class AddButton {
  constructor({ productId, inStock, onAdd }) {
    this.productId = productId
    this.inStock = inStock
    this.onAdd = onAdd
  }

  add() {
    if (this.inStock) {
      this.onAdd(this.productId)
    }
  }

  render() {
    return av!{ <button @click={add}>Add to cart</button> }
  }
}

class Cart {
  constructor({ itemCount = 0 } = {}) {
    this.itemCount = itemCount
  }

  addItem(id) {
    this.itemCount++
  }

  render() {
    return av!{
      <div>In cart: {itemCount}</div>
      <AddButton productId={1} inStock={true} onAdd={addItem} />
    }
  }
}
```

Rules — all mechanical, none requiring the compiler to understand what a
method *does*, only what it *names*:

- **Constructor-destructured parameters are the component's fields.**
  Whatever a parent supplies for one is a prop value; a default in the
  destructuring (`itemCount = 0`) makes it optional. Function-typed →
  callback prop. Anything else → data prop.
- **A field mutated anywhere in a method is local state**, whether or
  not it started from a constructor default.
- **`@click={method}` / `@click={method(arg)}`** — no-arg and
  call-expression wiring, unchanged from every draft before this one.
- **Inside `av!{}`, bare identifiers resolve against the class.** No
  `this.` inside the macro; `this.` is required everywhere else, because
  everywhere else is ordinary TypeScript.
- **`<ChildComponent propName={value} />`** — JSX-shaped, one attribute
  per constructor field. The value must be either a literal, a local
  field, or a local method name — never a computed or conditional
  expression (§3.4).
- **`{expr}` in child position** → a text node, auto-tracked, no marker.
  **`{expr}` in attribute position on a property that isn't naturally
  textual** (`<div innerHTML={dialog}>`, `<input value={username}>`) →
  a property binding instead of a text binding; two-way for form
  controls, one-way otherwise. This is the only thing standing in for
  the `:field="prop"` syntax explored earlier — folded into the same
  `{}` grammar rather than kept as a separate one.

## 2. What the compiler generates

Three passes, none of them touching a method's control flow.

### 2.1 Classify the constructor

Every destructured parameter becomes either a `props` entry (`fn` if its
declared type is a function, `data` otherwise) or contributes to the
component's field list. This is a read of the parameter list, not an
analysis.

### 2.2 Scan each method once

Walk the body for `this.field` references — read, write, or both
(`x++`). This produces `reads` per action. It's the one pass that's
irreducibly necessary in every version this design went through,
because it's what keeps the wire payload to exactly the fields an action
touches.

### 2.3 Lower JSX attribute lists

`<AddButton productId={1} inStock={true} onAdd={addItem} />` splits
mechanically on `AddButton.meta.props`: anything typed `fn` in the
target's props goes into the function-props map (as a *name*, `'addItem'`
— resolved against methods on the enclosing class), everything else goes
into the data-props map:

```js
renderChild(AddButton, { productId: 1, inStock: true }, { onAdd: 'addItem' }, 'Cart', parentRef, ref)
```

**Forwarding case:** if the value bound to a callback prop is itself a
prop of the *current* component (`<AddButton onAdd={onAdd} />` inside a
component that received `onAdd` from further up), the compiler doesn't
try to resolve a method — it emits a forward marker, and `renderChild`
copies whatever concrete `{component, ref, action}` record *this*
instance already holds for that prop. This is a copy, not a re-derivation,
and it's why nesting depth is a compile-time detail only — by the time
anything reaches the browser, every callback prop has already been
flattened down to one concrete target, however many components it
passed through on the way. §5.3 works this through end to end.

### 2.4 Emit `meta`

```js
AddButton.meta = {
  state: ['productId', 'inStock'],
  props: { onAdd: 'fn' },
  actions: { add: { reads: ['productId', 'inStock'], params: [] } }
}
```

No functions in it, ever — just names. This is exactly the object that
was hand-written and run successfully before any of this syntax existed;
the compiler's whole job is producing it without the author typing it.

## 3. Runtime model

### 3.1 Render — once, with provenance baked in

```html
<div data-ref="root-cart" data-component="Cart" data-state='{"itemCount":0}'>
  <div>In cart: <span data-bind="itemCount">0</span></div>
  <div data-ref="product-1" data-component="AddButton"
       data-state='{"productId":1,"inStock":true}'
       data-props='{"productId":{"value":1},"inStock":{"value":true},
                    "onAdd":{"component":"Cart","ref":"root-cart","action":"addItem"}}'>
    <button data-action="add">Add to cart</button>
  </div>
</div>
```

`data-props` carries every prop — data and function alike — with where
it came from. This is the "keep the whole tree traceable" property:
nothing about a running page is a mystery, because every instance
declares its own provenance right there in its markup, readable in
devtools with no build artifact to decode.

### 3.2 Click → request

```json
{
  "component": "AddButton", "ref": "product-1", "action": "add",
  "reads": { "productId": 1, "inStock": true },
  "props": {
    "onAdd": { "component": "Cart", "ref": "root-cart", "action": "addItem",
               "reads": { "itemCount": 0 } }
  },
  "params": []
}
```

**Blanket rule:** every declared function prop on the clicked instance is
attached, with its target's current reads, on every request from that
instance — regardless of whether the specific action being called
actually reaches it. This is the one deliberate simplification in the
whole design: it replaces call-graph tracing (rejected — required
merging code across classes) and a dispatch table (rejected — extra
runtime machinery for no real gain over just calling a function) with
"attach everything, let the real `if` statement decide." The cost is a
few unused scalar values on some requests; the benefit is that no pass
anywhere has to trace which method might call which prop.

### 3.3 Server — real objects, real calls, nothing else

```js
let ctorArgs = { ...body.reads }
for (let [propName, ref] of Object.entries(body.props)) {
  ctorArgs[propName] = (...args) => {
    let target = new registry[ref.component](ref.reads)
    target[ref.action](...args)
    // diff target's declared state fields against ref.reads, record what changed
  }
}
let instance = new registry[body.component](ctorArgs)
instance[body.action](...body.params)
// diff instance's declared state fields against body.reads, record what changed
```

`onAdd` is a real closure. If `add()` calls it, `Cart` really gets
constructed and `addItem` really runs — with real arguments, since
they're passed through a real function call, not reconstructed from a
pre-declared params list. If `add()` doesn't call it (`inStock` false),
`Cart` is never constructed at all. This was run, not just designed:

```
inStock:true  → {"writes":{"root-cart":{"itemCount":1}}}
inStock:false → {"writes":{}}
```

### 3.4 Response → DOM

```json
{ "writes": { "root-cart": { "itemCount": 1 } } }
```

Keyed by concrete ref, never by component type — unambiguous even with
many instances of the same component on a page. Client does
`document.querySelector('[data-ref="root-cart"]')`, updates its local
state cache, and sets `textContent` on whichever `data-bind`-marked
descendant matches each changed key.

## 4. Guardrails

- A callback-prop's bound value in JSX must be a local method name or a
  local prop name (forwarding) — never a ternary or computed lookup. Both
  remaining resolvable shapes are cheap, mechanical lookups; this is the
  one restriction actually worth enforcing at compile time, because
  everything downstream (§2.3, §3.2) assumes a concrete target exists.
- Forwarding chains must terminate — a compile-time cycle check, since a
  prop can't be resolved by copying a chain that loops back on itself.
- Every field a method reads or writes must be a real constructor field
  — no untracked reads.

## 5. Worked examples

### 5.1 Local action — no props involved

`Cart`'s own `addItem`, called directly (no `AddButton` in the picture):
request `{"component":"Cart","ref":"root-cart","action":"addItem","reads":{"itemCount":0},"props":{},"params":[5]}`
→ `{"writes":{"root-cart":{"itemCount":1}}}`.

### 5.2 Controllable property binding

```tsx
class Dialog {
  constructor({ content = '' } = {}) { this.content = content }
  update() { this.content = renderServerSide(SomeComponent) }
  render() {
    return av!{
      <div innerHTML={content}></div>
      <button @click={update}>update</button>
    }
  }
}
```

`content` never appears as `{content}` in child position — only as an
attribute-position binding, which is what tells the compiler to bind
`innerHTML` specifically rather than a text node. Response:
`{"writes":{"<ref>":{"content":"<div>...</div>"}}}` — client sets
`el.innerHTML` directly on the bound div, touches nothing else.

### 5.3 Multi-level forwarding

```tsx
class AddButtonWrapper {
  constructor({ onAdd }) { this.onAdd = onAdd }
  render() { return av!{ <AddButton productId={1} inStock={true} onAdd={onAdd} /> } }
}

class Cart {
  constructor({ itemCount = 0 } = {}) { this.itemCount = itemCount }
  addItem(id) { this.itemCount++ }
  render() {
    return av!{ <AddButtonWrapper onAdd={addItem} /> }
  }
}
```

Compiling `Cart.render()`: `onAdd={addItem}` is a local method — resolved
directly, same as §2.3's base case. Compiling `AddButtonWrapper.render()`:
`onAdd={onAdd}` is *itself* a prop of `AddButtonWrapper` — a forward
marker, not a new resolution. At render time, `AddButtonWrapper`'s own
`onAdd` was already given the concrete `{component:'Cart', ref:'root-cart',
action:'addItem'}` record when *it* was constructed, and that's what gets
copied into `AddButton`'s `data-props`. The click handler inside
`AddButton`, three components down from the actual state, does exactly
the same one-hop lookup as §3.2 — depth was resolved entirely at compile
time, and the runtime never knows it happened.

## 6. Deferred / out of scope

- **List mutation** (add/remove/reorder within an array field) — planned
  separately via a compiler-generated array proxy, not designed here.
- **`@source`** for non-DOM state (localStorage, cookies) — skipped.
- **WebSocket transport** — same request/response shapes, just sent over
  a persistent socket with a correlation id instead of `fetch`; no
  protocol change, not yet built.
